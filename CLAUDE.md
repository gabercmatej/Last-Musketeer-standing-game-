# CLAUDE.md — The Last Musketeer Standing

A Unity 6 multiplayer simultaneous-turn arena game for 4 friends (Matej, Matic, Aljaž, Nik). You (Claude Code) write most of the code. Matej directs, tests and makes the art.

**Target platform: Unity Web build (WebGL 2), hosted on Netlify. Everyone, including the host, plays in the browser on Mac or Windows.** Multiplayer goes through Unity Relay over secure WebSockets.

## Read first
- `docs/GAME_DESIGN.md` is the **rules source of truth**. Implement it exactly.
- `docs/TECH_DESIGN.md` covers the architecture, network protocol and testing.
- `docs/BUILD_PLAN.md` says what today's task is.
- `docs/DECISIONS.md` is where you log every ambiguity you resolve and every rule or balance change (one line each).

If a rule is ambiguous, pick the simplest deterministic interpretation, implement it, log it in DECISIONS.md and mention it in your summary. **Don't change the rules in GAME_DESIGN.md without asking.**

## Architecture rules (non-negotiable)
1. **The sim is pure C#** (`Assets/_Project/Scripts/Sim`, asmdef `Musketeers.Sim`, `noEngineReferences: true`). All gameplay rules live here and nowhere else.
2. **The sim is deterministic:**
   - integers only, with no `float` or `double`
   - no `System.Random`, `UnityEngine.Random` or time; use `DeterministicRng`
   - no iteration order taken from `Dictionary` or `HashSet`
   - resolve ordering ties with initiative or unit id
3. **Presentation never mutates game state.** It renders `GameState` and plays back `EventLog`.
4. **The network only carries plans, seeds, lobby data and hashes.** No NetworkTransforms, and no NetworkObjects per unit. There's one `MatchNet` and one `LobbyNet`.
5. **`MatchController` doesn't know whether it's online.** It talks to `IMatchTransport` (`LocalTransport` or `NetTransport`).
6. **All tuning numbers live in `GameConfig`**, matching GAME_DESIGN §11.
7. **There is one scene, `Main.unity`, and it's generated by an idempotent editor script** (`Tools/Musketeers/Build Main Scene`). Prefer changing the builder script and re-running it over hand-editing the scene through MCP, so the scene stays reproducible.
8. **UI uses UI Toolkit** (UXML/USS files in `Assets/_Project/UI`), with small controller classes.
9. **Personal content is data, not code:** names, colors, lines, award names and art go in `CharacterDef` and other ScriptableObjects or text assets.

## Web platform rules (see TECH_DESIGN §7)
- **No threads:** never use `Task.Run`, `Thread`, `Parallel` or blocking waits. `async/await` on the main thread is fine.
- **Relay protocol:** use `RelayProtocol.Default` (WSS on Web). Never mix Editor and browser players in one session.
- **Auth:** use a random auth profile per page load on Web, and a profile per virtual player in Multiplayer Play Mode.
- **Clipboard** goes through `Assets/Plugins/WebGL/Clipboard.jslib`. The invite link comes from `Application.absoluteURL` plus `?join=CODE`.
- **Storage** uses `PlayerPrefs` only, then `PlayerPrefs.Save()`. Don't use `System.IO` file writes.
- **Keys:** avoid browser-reserved keys (Ctrl/Cmd combos, F1–F12, Alt combos).
- **Stripping:** keep Managed Stripping at Minimal. If a Web build fails at runtime with missing types, add them to `link.xml` instead of raising stripping.
- **Test on Web regularly,** not just in the Editor. Some bugs only appear in the browser.
- To deploy, build to `Builds/Web` and run `tools/deploy-web.sh`. Bump Player Settings → Version first, because the lobby rejects mismatched versions.

## Working with Unity through MCP
- Write C# and UXML/USS files directly. Use the Unity MCP to:
  - refresh and compile, then **read the console**
  - run tests
  - enter and exit Play mode
  - run editor menu items such as the scene builder
  - inspect the scene or hierarchy when needed
- **After every batch of script changes, check the console for compile errors before moving on.** Never leave the project in a non-compiling state.
- **Before saying a task is done, run the EditMode tests via MCP.** Report the pass/fail counts.
- Don't create `.meta` files by hand. Let Unity generate them.
- If the MCP connection drops, tell Matej to check Window → MCP for Unity. Don't try to work around it.
- Check package APIs against the **installed version** (look in `Packages/manifest.json` and the package docs) before using them, especially Multiplayer Services Sessions and NGO 2.x RPCs.

## Testing
- Every rule gets an EditMode test, written with the ASCII `Scenario` helper (TECH_DESIGN §6).
- Keep the determinism test and fuzz test green at all times.
- The balance report test is in category `Balance`. It's excluded from normal runs, and you run it on request.
- Multiplayer: test with Multiplayer Play Mode (host + virtual players), each with its own auth profile.

## Code style
- Namespaces: `Musketeers.Sim`, `Musketeers.Game`, `Musketeers.Net`, `Musketeers.Presentation`, `Musketeers.UI`, `Musketeers.Data`, `Musketeers.EditorTools`.
- PascalCase for types and methods, `_camelCase` for private fields, and `[SerializeField] private` instead of public fields in MonoBehaviours.
- Keep files small and focused. `TurnResolver` is a partial class split by phase.
- Avoid allocations in the sim's hot paths (use structs, fixed-size plans and reusable lists), but correctness beats speed.
- Comment the *why* in the rules code and reference the GAME_DESIGN section, for example `// §6 Phase 3.4`.

## Placeholder art
Until Matej's art arrives:
- The project is **URP 2D**: everything is SpriteRenderers on a grid, seen by an orthographic top-down camera.
- Units are circle sprites tinted with the `CharacterDef` color, with a name label.
- Tiles are colored square sprites.
- FX are simple 2D particle systems or tweens.

Always keep a placeholder fallback when real art is missing, so the game never breaks because of a missing asset.
